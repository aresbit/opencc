# 多核调度：实测出来的结论，和一个反直觉的结果

目标是让 opencc 把 runtime 调度到多个 CPU 核，支撑几千个 subagent 共享一个上下文。

这份文档记录**先量后写**的过程，因为量出来的结果和直觉相反：
**在你说的规模上（几千个 agent），单线程本来就够，多核几乎没有收益。**
真正的收益来自另一处，而且不需要线程。

---

## 一、agent 到底是不是 CPU-bound

不是。一个 LLM agent turn ≈ 2000ms 网络等待 + 1ms 以下的 CPU。
占空比 0.05%，事件循环远没有饱和。

实测单线程扩展曲线（579 KB 共享上下文，2s 网络延迟，4 核机器）：

| 并发 agent | 墙钟 | 超出网络时间的排队 | 新增 RSS |
|---|---|---|---|
| 1,000 | 2.5s | 0.04s | 6 MB |
| 5,000 | 4.0s | 0.03s | 5 MB |
| **10,000** | 5.2s | **1.16s** | 4 MB |
| 20,000 | 7.1s | 3.07s | 6 MB |
| 40,000 | 11.0s | 6.96s | 11 MB |

**单线程的拐点在 5,000–10,000 之间。** 内存完全不是约束 ——
每个 agent 上下文实测 0.32 MB 堆占用，3000 个不到 1 GB。
64 GB / 16 核的机器上，内存能放下的远比事件循环能调度的多。

## 二、把 agent 分片到 worker：6% 提升

每个 worker 端到端拥有一批 agent（自己的事件循环、自己的 turn 循环），
消息只在开始和结束穿越线程 —— 这是"调度到其他 CPU"最正统的实现方式。

2000 agents × 3 turns：

| | 墙钟 | 排队 |
|---|---|---|
| 单线程 | 6.6s | 0.02s |
| 2 workers | 6.3s | 0.02s |
| 3 workers | 6.2s | 0.04s |

**6% 提升。** 因为要并行的那点 CPU 本来就不存在。

## 三、按任务卸载到 worker 池：更慢

最初的设计是把每个 turn 的序列化/解析丢给 worker 池。实测**变慢**：

| | 墙钟 | 排队 |
|---|---|---|
| 单线程 | 3.4s | 0.01s |
| 池 + 共享上下文 | 4.1s | 2.04s |

原因是每 turn 两次 `postMessage` 往返，而 turn 的 CPU 只有 ~1ms ——
**往返延迟和被卸载的工作同量级**，池子自己成了新的队头。

这里还撞到一条更根本的约束：

> **数据在主线程堆里时，搬到 worker 的成本等于在主线程干掉它的成本。**

`submit('parse', { text: 大字符串 })` 会 structured-clone 那个字符串。
克隆和解析同量级，所以永远不赚。只有**零拷贝**（SharedArrayBuffer 或
transferable）才可能赚。用 transfer 重测：

| | 主线程阻塞 | 墙钟 |
|---|---|---|
| 主线程解析 300 × 96 KB | 83 ms | 83 ms |
| 池 + transfer | **7 ms（12.5× 少）** | 187 ms（2.3× 慢） |

**池子不让 CPU 活变快，它让这些活不再堵住别人。** 这是延迟公平性换吞吐，
在超过单线程拐点时是对的取舍，在拐点以下是纯亏。

## 四、真正有收益的地方：共享上下文，且不需要线程

我第一版实验在 2000 agent 就看到 1.8s 排队 —— 因为那版**每 turn 重新序列化整个
579 KB 上下文**。这才是真的瓶颈，而它的解法与多核无关：

把共享前缀**预编码成 UTF-8 字节存进 SharedArrayBuffer**，每次请求只拼接
`共享字节 + 本 agent 的 delta`，不再序列化前缀。

| 组装一个请求体 | 耗时 |
|---|---|
| 重新序列化整个上下文（现状） | 0.776 ms |
| 拼接预编码共享字节 + delta | **0.288 ms** |

**2.7× 更便宜，纯主线程，零线程参与。** 而且它把单线程拐点从 ~2,000
推到了 ~10,000 —— 也就是说，**你要的"几千个 agent"是靠这一条解决的，不是靠多核。**

## 落地的东西

| 文件 | 作用 |
|---|---|
| `src/services/parallel/sharedContext.ts` | 共享上下文：预编码进 SAB，跨线程按引用传递，`concatBytes` 零拷贝组装 |
| `src/services/parallel/workerPool.ts` | worker 池：按核数减一、有界队列背压、worker 崩溃后重建并补发 fragments |
| `src/services/parallel/workerSource.ts` | worker 源码内联为字符串（opencc 打包成单文件，独立 worker 文件在 bundle 里会消失） |

几个刻意的设计决定：

- **fragment 不可变**，所以无锁共享是安全的而不只是快：系统提示变了就发布新
  fragment，旧的等最后一个读者用完自然释放。已取走 handle 的 worker 不会被抽走内存。
- **按 UTF-8 字节长度分配**，不是字符串长度 —— 否则中文系统提示会被截断。
- **有界队列**：几千个 agent 提交速度可以超过任何池的消化速度，无界队列会把
  背压信号变成进程被 OOM 杀掉。
- **worker 池默认 核数-1**：主线程还有编排和 REPL 要跑，把核占满等于和自己抢。

## 什么时候用

- **共享上下文：几乎总是值得**，只要多个 agent 共享同一个前缀。
- **worker 池：只在超过单线程拐点（~5k–10k 并发）时，或者真正 CPU-bound
  且数据能零拷贝送过去时。** 在此之下它是净亏，测量在上面。
- opencc 真正 CPU-bound 的活（CodeAct、Bash）**已经在独立进程里**，本来就用着别的核，
  不需要 worker。

## 没做的

把共享上下文接进真实的 agent 请求路径（`services/api/claude.ts` 的 body 组装）。
那要改请求构造的核心路径，值得单独一轮并配 before/after 实测。
现在落的是经过验证的地基和它的数据。
